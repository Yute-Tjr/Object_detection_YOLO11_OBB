# 部分区域反馈与部署流程改进设计

## 目标

本次改动解决三个关联问题：反馈弹窗中的区域顺序混乱、反馈必须填写所有区域、Docker 部署缺少合理的镜像回退顺序和用户创建流程。

完成后：

1. 所有反馈区域按 `label1` 到 `label6` 的逻辑顺序显示。
2. 用户只反馈需要纠正的区域，服务端仍保存该图片全部检测区域的结果快照。
3. 数据库能够区分人工反馈、沿用模型结果和未分类区域。
4. Docker 构建依次尝试 Docker Hub、国内镜像、本地缓存。
5. 首次部署必须创建登录用户，更新部署可以选择新增用户。
6. 数据库密码和网页登录密码最低长度统一为 6 位。

## 范围与约束

- 保留现有用户名大小写敏感规则、Argon2id 密码哈希和服务端会话机制。
- 不增加网页注册、网页重置密码或用户管理页面。
- 不在 `.env`、部署日志、命令参数或 Git 中保存网页登录密码。
- 数据库密码仍只允许字母、数字及 `._~-`，以保证 PostgreSQL URL 可安全解析。
- 同一用户对同一图片仍只有一份可覆盖更新的反馈。
- 任务一旦包含反馈，仍禁止删除。
- `label1_thin` 和 `label1_thick` 在反馈界面统一为 `label1`，但数据库继续关联真实检测记录。

## 反馈显示顺序

后端在构建反馈视图时按照逻辑区域排序：

```text
label1, label2, label3, label4, label5, label6
```

同一逻辑区域出现多个检测框时，以检测框原始稳定顺序作为次级顺序。漏检候选区域使用同一顺序。前端不依赖数据库返回顺序，并使用同一个顺序函数进行防御性排序。

## 部分区域反馈交互

每个已检测区域具有两种编辑状态：

- **沿用原结果**：用户未对该区域作人工判定。
- **人工反馈**：用户明确选择该区域，并填写实际结果。

默认情况下，没有历史人工反馈的区域保持“沿用原结果”。用户启用某个区域的人工反馈后：

- 必须选择 `OK` 或 `NG`。
- 若逻辑区域为 `label1`，还必须选择 `B/G/R/W` 中的一种颜色。
- 用户可以取消该区域的人工反馈，使其恢复为沿用当前模型结果。

提交时至少包含一个人工反馈区域或一个漏检区域；完全空白的提交被拒绝。漏检区域仍只从当前未检测到的逻辑区域中选择。

再次打开已有反馈时，人工反馈区域恢复为可编辑的人工值；模型和未分类区域显示其来源及快照值，但不伪装为人工确认。

## 完整结果快照

API 继续接收用户实际选择的部分检测项，服务端负责把请求扩展成当前图片全部检测区域的快照。客户端不能伪造未提交区域的来源。

每个 `image_feedback_items` 记录新增 `source` 字段，并允许 `verdict` 为空：

| source | 含义 | verdict | color |
| --- | --- | --- | --- |
| `manual` | 用户明确反馈 | 必须为 `OK/NG` | `label1` 必须为 `B/G/R/W`，其他区域为空 |
| `model` | 用户未反馈，沿用模型输出 | 有异常分类时保存 `OK/NG`，否则可为空 | 有受支持颜色输出时保存标准颜色，否则为空 |
| `unreviewed` | 用户未反馈且无任何可沿用分类结果 | 空 | 空 |

来源判定规则：

1. 请求包含该 `detection_id` 时使用 `manual`。
2. 未包含时，从检测记录关联的分类结果读取异常判定和颜色。
3. 至少存在一个有效模型分类值时使用 `model`。
4. 不存在可用分类值时使用 `unreviewed`。

只接受标准值：异常结果必须是 `OK/NG`，颜色必须是 `B/G/R/W`；不认识的模型输出不写入人工真值字段。服务端仍校验提交的检测 ID 属于当前图片、无重复且图片已处理完成。

现有 `image_feedback_items` 都来自旧版强制人工填写流程，迁移时统一设置 `source=manual`。新字段使用字符串和检查约束，避免数据库枚举带来的后续迁移成本。

API 响应在每个反馈项中返回 `source`、可空的 `verdict` 和可空的 `color`。这使导出程序能够直接区分人工纠正、模型快照和未评审区域。

## 镜像构建回退

服务镜像构建顺序固定为：

1. 使用 Docker Hub 基础镜像并执行拉取构建。
2. 仅当日志明确属于 Docker Hub 网络或认证服务不可达时，切换国内镜像并执行拉取构建。
3. 国内镜像仍因仓库网络问题失败时，恢复默认镜像名称并使用本地缓存构建，不主动拉取。
4. 本地缓存也不可用时终止部署，输出统一日志文件位置和最后一次错误。

Dockerfile 语法错误、依赖安装错误、前端构建错误等非仓库网络故障直接终止，不进行镜像源回退。BuildKit 非打印字符错误仍在同一来源下自动重试一次。

PostgreSQL 首次启动的镜像回退使用同样顺序：Docker Hub、国内镜像、本地缓存。切换镜像源只作用于当前部署进程，不修改 Docker Desktop 全局设置，也不永久写入 `.env`。

## 部署密码和用户创建

### 密码规则

- 数据库密码至少 6 位，拒绝空值和示例占位符，保留 URL 安全字符限制并要求二次输入一致。
- 网页用户密码至少 6 位，要求二次输入一致，继续通过 Argon2id 存储。
- 旧用户密码哈希无需迁移，登录验证保持兼容。

### 首次部署

交互式首次部署在配置数据库后要求输入：

- 初始登录用户名；
- 初始登录密码；
- 再次输入初始登录密码。

用户名使用现有 `normalize_username` 规则。凭据仅保留在当前部署进程内存中，不进入配置摘要、`.env` 或部署日志。数据库迁移完成且 API 可用后，通过管理脚本创建初始用户；创建失败则部署返回非零状态并给出原因。

`--yes` 非交互首次部署必须通过 `INITIAL_APP_USERNAME` 和 `INITIAL_APP_PASSWORD` 提供初始用户；缺失时在部署前终止。部署脚本向容器的标准输入传递两次密码，不把密码放入命令参数。

### 更新部署

交互式更新部署询问“是否新增网页登录用户”。选择是时收集用户名及两次密码，并在数据库迁移后调用现有 `add` 命令。选择否则不改变用户。

非交互更新默认不新增用户；仅当同时提供 `INITIAL_APP_USERNAME` 和 `INITIAL_APP_PASSWORD` 时新增。用户名已存在时不自动重置密码，部署终止并提示使用：

```bash
docker compose exec api python scripts/manage_users.py reset-password USERNAME
```

## 错误处理

- 反馈提交的手工项为空且漏检为空：返回 `422`。
- 手工项缺少判定或 `label1` 缺少颜色：返回 `422`。
- 检测结果在页面打开后发生变化、检测 ID 不属于图片或重复：返回 `409/422`，前端保留草稿并提示重新加载。
- 初始用户创建失败：不回滚已完成的数据库迁移和镜像构建，但部署脚本以失败结束并显示可重复执行的用户管理命令。
- 镜像回退只响应可识别的仓库网络错误，其他错误不隐藏。
